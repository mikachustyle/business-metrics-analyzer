# Ответы на контрольные вопросы

**Практическое занятие № 1**  
Дисциплина: «Проектирование и разработка бизнес-ориентированного программного обеспечения»

## 1. Чем отличается Git от GitHub?

Git — система контроля версий, которая хранит историю изменений файлов и позволяет создавать ветки, сравнивать версии и объединять изменения. Git работает на компьютере и может использоваться без GitHub.

GitHub — интернет-платформа для хранения Git-репозиториев и совместной работы. На ней можно создавать Pull Request, обсуждать изменения и проверять код.

## 2. Для чего используется виртуальное окружение Python?

Виртуальное окружение изолирует библиотеки и их версии для отдельного проекта. Это позволяет устанавливать зависимости проекта, не затрагивая другие проекты и системную установку Python.

В нашей работе окружение находится в папке `.venv`, а список зависимостей сохраняется в `requirements.txt`.

## 3. Что такое commit, branch, remote, pull request?

- **Commit** — фиксация подготовленных изменений в истории репозитория с сообщением, автором и уникальным идентификатором. Коммит создаётся локально; для отправки на GitHub требуется `push`.
- **Branch** — ветка разработки, позволяющая работать над изменениями отдельно от основной ветки `main`.
- **Remote** — именованная ссылка на удалённый репозиторий. Обычно основной удалённый репозиторий называется `origin`.
- **Pull Request** — запрос на проверку и слияние изменений из одной ветки в другую на GitHub. Он позволяет обсудить код, оставить замечания и объединить изменения после проверки.

## 4. Зачем нужен файл .gitignore?

`.gitignore` задаёт правила исключения файлов и папок из добавления в Git. В нём указывают виртуальное окружение `.venv`, кэш Python, временные файлы и файлы с секретами. Это помогает не отправлять ненужные данные в репозиторий.

Если файл уже отслеживается Git, добавление его в `.gitignore` само по себе не прекращает отслеживание и не удаляет его из истории.

## 5. Как организовать командную работу над бизнес-приложением с помощью Git?

Участники используют общий репозиторий на GitHub, а каждый разработчик имеет его локальную копию.

1. Перед началом работы получают актуальную версию `main` и создают отдельную ветку для своей задачи.
2. Вносят изменения, проверяют программу, делают коммит и отправляют ветку командой `push`.
3. Создают Pull Request и назначают другого участника для проверки.
4. Исправляют замечания и выполняют слияние с `main`.
5. Оба участника обновляют локальную `main` командой `pull`.

В нашем проекте Разработчик 1 добавляет расчёт KPI в `feature/add-kpi-calculation`, а Разработчик 2 дополняет README в `feature/add-docs`.

## 6. Какие файлы обязательно должны быть в репозитории учебного проекта?

Для основной практической части нужны:

- `main.py` — код программы;
- `README.md` — описание проекта и инструкция запуска;
- `requirements.txt` — список зависимостей;
- `.gitignore` — правила исключения ненужных файлов.

Для домашнего задания дополнительно нужен `docs/business_requirements.md` с кратким описанием бизнес-требований.

Папку `.venv` и секретные данные в репозиторий не добавляют. Папка `.git` хранит локальную историю и настройки Git и не добавляется как обычная папка проекта.

## 7. Что произойдёт, если два разработчика изменят один и тот же файл в разных ветках?

Изменения сначала сохранятся независимо в своих ветках. При слиянии Git обычно автоматически объединяет изменения, если они затрагивают разные участки файла.

Если изменён один и тот же участок несовместимым образом, возникнет конфликт слияния. Разработчики должны согласовать итоговое содержимое, убрать маркеры конфликта, проверить результат, добавить исправленный файл в индекс и завершить слияние коммитом.

Сам факт изменения одного файла в двух ветках не всегда приводит к конфликту.
